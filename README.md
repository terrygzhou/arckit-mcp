# arckit-mcp

Standalone ArcKit MCP server — exposes the ArcKit architecture-governance harness
as MCP tools so an AI agent can inspect projects, check gate tiers, walk handoff
chains, and persist artefacts without leaving the session.

## Package layout

```
arckit_mcp/
    __init__.py
    __main__.py
    _registry.py   # generated by scripts/generate-mcp-registry.py
    gates.py       # generated by scripts/generate-mcp-gates.py
    handoffs.py    # generated by scripts/generate-mcp-handoffs.py
    intake.py      # generated by scripts/generate-mcp-intake.py
    server.py      # MCP server entry point
    sync.py        # regenerate generated files from an installed ArcKit
tests/
    mcp/
        conftest.py
        test_agent_loop.py   # EYW-817 checkpoint suite (CP1–CP9 + invariants)
        test_gates.py
        test_intake.py
        test_next_step.py
        test_seed_context.py
        test_sync.py
```

## Dev loop

```bash
# Install the package (editable) into the shared venv
cd ~/.local/share/arckit-mcp && source .venv/bin/activate
pip install -e ~/projects/arckit-mcp

# Run the test suite
cd ~/projects/arckit-mcp
python -m pytest tests/ -v

# Regenerate _registry.py / gates.py / handoffs.py from the installed
# ArcKit source tree (requires `arckit` to be installed, or pass --source-root)
arckit-mcp-sync
arckit-mcp-sync --source-root ~/projects/arc-kit

# Regenerate intake.py from the sibling arc-kit checkout
ARCKIT_MCP_ROOT=$PWD python ../arc-kit/scripts/generate-mcp-intake.py

# Boot-test the MCP server
arckit-mcp
```

## Generators

The generated files (`_registry.py`, `gates.py`, `handoffs.py`, `intake.py`)
are produced by scripts that live in the `arc-kit` repo
(`scripts/generate-mcp-{registry,gates,handoffs,intake}.py`). Those scripts
default to writing into this repo's `arckit_mcp/` directory (sibling layout)
and accept `ARCKIT_MCP_ROOT` env var or a CLI arg to override the output path.

`arckit-mcp-sync` (in `arckit_mcp/sync.py`) is the convenience wrapper that
runs the registry, gates, and handoffs generators with the correct local
output paths. The intake generator (`generate-mcp-intake.py`) is run
directly: `python ../arc-kit/scripts/generate-mcp-intake.py` (sibling
checkout, with `ARCKIT_MCP_ROOT` set or a CLI arg for non-sibling layouts).

pip install ~/projects/arckit-mcp

pip install ~/projects/arckit-mcp[dev]   # includes arckit + pytest

## New machine

Three things: Python 3.11+, the repo, and (optionally) the arc-kit repo for
regenerating the vendored generated files.

1. **Prereqs**: Python ≥ 3.11, `git`. Any venv tool works; the examples use
   `uv` to match the dev loop.

2. **Clone and install**:

   ```bash
   git clone <arckit-mcp-repo-url> arckit-mcp
   git clone <arc-kit-repo-url> arc-kit        # only needed to regenerate generated files

   uv venv ~/.local/share/arckit-mcp/.venv
   source ~/.local/share/arckit-mcp/.venv/bin/activate
   pip install -e ~/projects/arckit-mcp[dev]    # [dev] pulls arckit + pytest
   ```

   The generated files (`_registry.py`, `gates.py`, `handoffs.py`,
    `intake.py`) are committed, so a plain `pip install` works standalone —
    no arc-kit required
    to *run* the server. arc-kit is only needed to **regenerate** them when the
    source commands change:

    ```bash
    arckit-mcp-sync --source-root ~/projects/arc-kit
    ARCKIT_MCP_ROOT=$PWD python ../arc-kit/scripts/generate-mcp-intake.py
    ```

3. **Register with your MCP client** (stdio server — `arckit-mcp` console
   script or `python -m arckit_mcp`), e.g. Claude, mirroring `arc-kit/.mcp.json`:

   ```json
   { "mcpServers": { "arckit": { "command": "/path/to/venv/bin/arckit-mcp" } } }
   ```

   Substitute the path to the new machine's venv.

4. **Verify**:

   ```bash
   python -m pytest tests/ -v      # 66 tests
   arckit-mcp                      # boots the stdio server; Ctrl-C to stop
   ```

## Using with ArcKit

The server exposes the ArcKit governance harness as MCP tools so an agent can
drive the harness without knowing its 101 commands and templates.
The agent never reads the command markdown itself — the server acts as a
*prompt relay*: it tells the agent which gates are open, what to answer, and
where to write the result, and the agent does the actual document generation
in-session (the LLM work). Artifacts land in the ArcKit tree with the
standard `ARC-{NNN}-{TYPE}...md` naming.

### What the tools do

There are two groups of tools.

**Meta-tools** — the ones an agent reaches for first. These carry the
governance logic, so the agent never has to know the command graph by heart:

| Tool | What it does |
| --- | --- |
| `arckit.seed_context` | Start a project tree (`projects/{NNN}/`, recorded with a slug in the `.meta` sidecar) with goals, constraints, and/or an imported context folder. Returns the `project_id` to use everywhere else. Ask the user for a context folder first if they haven't given one. |
| `arckit.list_commands` | Enumerate every known command with its doc-type codes and gate tiers. Useful for discovery, not required in the normal loop. |
| `arckit.next_step` | Walk the handoffs graph and return the next recommended command given the project id and the commands completed so far. |
| `arckit.check_gates` | Return which prerequisite gates are open/closed for a command. `MANDATORY` gates hard-stop when open; `RECOMMENDED` are noted; `OPTIONAL` are omitted. |
| `arckit.persist_intake` | Read saved intake answers (`.arckit/intake/{command-hyphenated}.json`). Read-only; never writes. |
| `arckit.persist_artifact` | Write a generated artifact into the project tree. Multi-instance types (ADR, DIAG, …) get the next sequence number when `sequence` is omitted. |

**Per-command tools** — one `arckit.{command}` tool per ArcKit command
(101 of them), e.g. `arckit.strategy`, `arckit.risk`, `arckit.roadmap`,
`arckit.it4it_value_network`. Each returns:

- `intake` — the intake questions to answer,
- `instructions` — where to run the generation and where to save the result,
- `gates` + `gate_blocked` — current gate status,
- `doc_type` — the doc-type code(s) the command writes.

The agent runs the generation in-session and persists each result via
`arckit.persist_artifact`.

### Intake question coverage

The `intake` field returned by each per-command tool is populated from
statically-generated `INTAKE` data (see `intake.py` in the generated
modules). The generated `COVERAGE` dict marks each doc-type code as
`covered` or `no-static-questions`. For doc-type codes that fall into
`no-static-questions` — which covers the large majority of doc-types in the
core `arckit-claude` plugin, since its templates ship no
`## Intake Interview Questions` blocks — the server degrades gracefully to
one **placeholder** question per code, mirroring the legacy behaviour.
This degradation is *intentional*: the server must never return an empty
question list for a known doc-type; the `COVERAGE` report makes the gap
visible so consumers can decide whether to warn the user or proceed.
Overlays (`togaf-adm`, `it4it`, `oaa`, `agent-architecture`) that *do*
ship question blocks are fully `covered`.

### The agent loop

1. **Seed** — `arckit.seed_context` to get a `project_id` (or reuse an
   existing project directory under `projects/`).
2. **Relay** — call the per-command tool, e.g. `arckit.strategy(project_id)`.
   Read `gate_blocked`: if a `MANDATORY` gate is open, go back to the
   prerequisite command first; otherwise answer the `intake` questions,
   generate the document, and persist it with `arckit.persist_artifact`.
3. **Advance** — call `arckit.next_step` with the commands completed so far
   to find the next one, then repeat from step 2.

All project-state lookups are relative to the server's working directory
(`projects/{project_id}/`), so launch `arckit-mcp` from the root of your
ArcKit working tree. `seed_context` mints the bare `projects/{NNN}/`
directory on disk (a slug is recorded in the `.meta` sidecar, and the
original project name is deduplicated against `.meta` files), and
`persist_artifact`, `check_gates`, and `_artifact_exists` all resolve the
same bare `projects/{project_id}/` directory.

### Worked example: a security architecture strategy in Australia

Say an agent is asked: "Design a security architecture strategy for our
platform that must comply with the Australian government's IRAP / Protective
Security Framework." The agent never needs to know ArcKit has 101 commands
— it just follows the loop above.

1. `arckit.seed_context` with the goal (PSF-aligned security strategy) and a
   constraints list (IRAP-assessed cloud, data-sovereignty region, …). This
   returns `project_id: "003"`.
2. `arckit.risk(project_id: "003")` → gate check shows `PRIN` (a MANDATORY
   gate) is open, so the agent first runs `arckit.principles` to produce the
   `PRIN` artifact, persists it, and re-checks.
3. Now `arckit.risk` passes → generate and persist the `RISK` artifact.
4. `arckit.next_step(project_id: "003", completed: ["principles", "risk"])`
   returns the next recommended command; the agent repeats the relay/persist
   step until the strategy document is complete.

The agent can also call `arckit.list_commands` at any point to discover a
command it hasn't used yet, rather than guessing. The whole exchange stays
inside one MCP session — no manual file juggling, no need to learn the
template catalog.
